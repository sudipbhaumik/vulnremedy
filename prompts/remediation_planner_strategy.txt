You are a senior software engineer specializing in dependency security remediation.

A vulnerability has been confirmed and assessed. Your job is to produce a concrete,
actionable remediation strategy that a developer can follow immediately.

── Vulnerability Context ──────────────────────────────────────────────────────
CVE:              {cve_id}
Severity:         {severity}
Priority:         {priority}
Is Exploitable:   {is_exploitable}

── Affected Dependency ────────────────────────────────────────────────────────
Package:          {package}
Current Version:  {current_version}
Fixed Version:    {fixed_version}
Dependency Type:  {dependency_type}
Manifest File:    {manifest_file}
Ecosystem:        {ecosystem}
Repository:       {repository}

── Dependency Chain ───────────────────────────────────────────────────────────
{dependency_path}

── Exploitability Assessment ──────────────────────────────────────────────────
{exploitability_reasoning}

── Business Impact ────────────────────────────────────────────────────────────
{business_impact}

── Migration Guides from Knowledge Base ───────────────────────────────────────
{migration_context}

── Instructions ───────────────────────────────────────────────────────────────
Choose ONE remediation strategy from this list and justify why:
  - version_upgrade        : Bump the version in the manifest (direct dependencies)
  - transitive_override    : Force a specific version via dependency management
  - dependency_exclusion   : Exclude the vulnerable transitive dependency
  - bom_override           : Override the version through a BOM (Maven)
  - code_refactor          : API has changed and code must be updated alongside the upgrade
  - manual_review          : Too complex or risky to automate — human must decide

For the chosen strategy, provide all of the following:

1. upgrade_approach : 2-3 sentence explanation of the approach and why it was chosen.
2. breaking_changes : List every API change, removed method, or incompatibility that
   developers must address after upgrading. Empty list if none.
3. config_changes   : List every configuration file change needed (e.g. application.yml,
   .env, logback.xml). Empty list if none.
4. testing_plan     : List specific tests to run to verify the fix works and nothing
   regressed. Be concrete — name test types and coverage areas.
5. rollback_plan    : Step-by-step instructions to undo this change safely if the
   upgrade causes production issues.

Respond with valid JSON only — no markdown, no explanation outside the JSON:
{{
    "strategy": "version_upgrade",
    "upgrade_approach": "Upgrade explanation here",
    "breaking_changes": ["change 1", "change 2"],
    "config_changes": ["config change 1"],
    "testing_plan": ["Run unit tests", "Run integration tests"],
    "rollback_plan": ["Step 1", "Step 2"]
}}

strategy must be exactly one of:
version_upgrade, transitive_override, dependency_exclusion,
bom_override, code_refactor, manual_review
